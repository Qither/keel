## 威胁模型

keel 是一个协作式的本地进程，而不是操作系统级的安全沙箱。在原生 Windows 上，大多数智能体 CLI 以用户的完整文件权限运行，因此 keel 并不承诺席位（seat）无法触及某些东西。它承诺的是：重要的事情要么在运行时和操作系统允许的范围内被阻止，要么在事后被检测到，并且会按运行时和操作系统说明属于哪一种（KP-16）。这些保证建立在四件在每个梯级上都成立的事情之上：对照当前内容核对的董事会（Board）批准记录、Steward 重新执行、引用快照和哈希链。根据所有者声明（D6，[00-mandate.zh-CN.md](00-mandate.zh-CN.md)），keel 保护的是人的决定权，以及“所批准的内容”与“实际运行的内容”之间的一致性；它不防御在同一操作系统账户下运行的恶意程序，下文的每项保证都在这一界限之内陈述。

### 资产

| 资产 | 存放位置 | 为何重要 |
| --- | --- | --- |
| 董事会权威 | 坐在交互式终端前的董事会成员；`.keel/approvals/` 与 `approval.recorded` 事件 | 每个检查点（checkpoint）、裁定（ruling）、策略和治理文档的效力都来自董事会对所展示内容的显式确认。 |
| 主干历史 | 本地及共享远端上的 `refs/heads/<trunk>` | 已落地的代码就是产品；它只能通过 `keel land` 或明确的董事会操作移动。 |
| 冻结意图（frozen intent）与契约 | `intent.md` 冻结块、`contract_hash`、`.keel/charter.md`、`.keel/goals.yaml` | 悄悄削弱验收标准是最具破坏性的对齐失败。 |
| 证据与评审结论（verdict） | `.git/keel/records/`、归档投影 | "完成"意味着 keel 重新执行过的证据。 |
| 账本 | `.git/keel/ledger/<yyyy-mm>.jsonl` | 事件的唯一真相存储；所有状态都由它计算得出。 |
| 模型提供方取值与运行时凭据 | 用户的环境、运行时主目录和凭据文件 | 它们属于用户（P1）。keel 从不打开它们，也不得让席位读取它们。 |

### 参与者与信任级别

| 参与者 | 信任 | 运行身份 | 说明 |
| --- | --- | --- | --- |
| 董事会 | 受信任；唯一的权威 | 坐在交互式终端前的人 | 只通过 `keel approve` 批准，且在查看变更之后。 |
| Steward（keel 核心） | 受信任的代码 | 用户的操作系统账户 | 确定性的；从不在自身进程中调用模型。 |
| 席位进程 | 输出是不可信数据 | 用户的操作系统账户（独立的席位操作系统账户是 M6 的评估项，[17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md)） | 一个智能体 CLI 加一个模型，以无头方式启动，使用按运行生成的配置。 |
| 直连通道（direct lane）子进程 | 无工具；输出不可信 | 由 Steward 启动的独立子进程（M6） | 仅在调用时于内存中持有一个已路由配置的取值。 |
| 模型提供方 | 外部；归用户所有 | 在本机之外 | keel 只知道环境变量名、协议 id 和别名。 |
| 仓库内容与第三方文本 | 不可信数据 | n/a | 源文件、issue 文本、测试输出、抓取的页面。 |
| 共享 git 远端 | 在 keel 之外 | 代码托管平台或服务器 | 由服务端规则保护（见最后一节）。 |

### 不在范围内

- 恶意或已被入侵的董事会成员。在终端上做出的确认按定义就是权威。
- 操作用户操作系统账户的恶意软件或他人。这样的进程可以运行 `keel approve`、写入记录、账本行和锚点引用，并重新计算每一个哈希；根据所有者声明（D6），keel 不声称能检测到这种情况。在需要多用户问责的场合，问责来自代码托管平台自身的身份和服务端规则（见最后一节），而不是来自 keel 的记录。
- 证明某个具名批准人究竟是谁。批准人字段是一个声明的本地名字；批准时间是本地时钟。
- 席位进程的网络出口。keel 不过滤网络流量；拥有 shell 工具的席位能以用户的权限访问网络。
- 模型提供方侧的行为、模型质量和套餐条款。doctor 会提醒用户检查自己的套餐条款，但不对其作任何断言。
- 仓库内容对董事会所路由到的模型提供方的保密性。路由是董事会的决定，记录在已批准的 `.keel/routing.yaml` 中。
- 从多台机器并发使用。v1 仅支持单机（[17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md)）。

## 批准记录：能证明什么，不能证明什么

一个批准是对所展示内容的显式确认，由 `keel approve` 记录。其机制（流程、记录结构、每种类别绑定什么、门禁如何检查）位于 [02-alignment.zh-CN.md](02-alignment.zh-CN.md)。本节陈述从该设计中推出的保证，以及推不出的保证，以免其他任何文档声称得更多。相应决策是 [ADR-0005](adr/ADR-0005-explicit-confirmation-approvals.zh-CN.md)。

### 记录绑定了什么

| 字段 | 绑定内容 | 验证方式 |
| --- | --- | --- |
| `subject`、`kind`、`stage` 或 `rule` | 董事会所看到的那一个事项 | 门禁要求完全匹配 |
| `artifacts[].sha256`、`contract_hash`、`request`、`land.receipt_draft` | 董事会所查看的内容版本，以规范化字节表示 | 在每道门禁处重新哈希并比对；任何差异都使批准失效 |
| `commit` | 产物是在哪里读取的 | 门禁在该提交处、或在承载它的分支上读取产物 |
| `ledger_chain_head` | 记录时的账本状态 | `keel audit` 检查该链头是否位于已验证的链上 |
| `approver.name` | 做出确认的人所声明的身份 | 只记录；从不验证 |
| `approved_at` | 确认时的本机时间 | 只记录；从不验证 |
| `note` | 可选的备注 | 只记录；从不解释 |

哈希就是绑定的全部。它们恰好覆盖记录所列出的产物，用其他所有 keel 哈希所用的规范化规则计算；对所列产物的变更会使批准失效，对其他任何地方的变更则不会。记录从不哈希自身。

### 记录不能证明什么

- **身份。** 批准人字段是来自个人配置或提示处输入的一个名字。keel 记录它，但不对其做身份验证。记录不能证明具名的那个人、或任何特定的人按下了那个键。
- **时间。** `approved_at` 是本地时钟，不是可信的时间戳。
- **在另一台机器上的真实性。** 提交到 git 的记录可以在任何克隆上读取，其哈希可以与那里的内容比对，因此克隆能看到批准了什么、批准的是哪个版本。但克隆无法区分一条由 `keel approve` 写出的记录与一条由同等权限的进程写出的记录；keel 不作这样的声称。
- **抵御同一账户下的进程。** 哈希链、锚点引用和每条记录中的链头能检测那些让链不一致的编辑。一个拥有用户权限、把记录、账本行和锚点一起改写的进程会保持一致，因而不会被检测到。根据所有者的声明，这不在范围内；keel 是一个协作式的本地进程。

### 确认与拒绝规则

- `keel approve` 在提出任何要求之前先展示主题及其变更，然后要求输入确认词（在 Git Bash mintty 下 Node 看不到 TTY，此时要求输入所显示的确认码）。单独按 Enter、泛泛的“继续”或其他任何输入都是拒绝。
- 在 `KEEL_RUN` 或 `KEEL_RUN_ID` 下，以及当某个祖先进程是已登记的 keel 运行时，它拒绝执行。Windows 上的祖先进程遍历有待探测验证。
- 确认之后，它重新哈希被绑定的产物，若有任何一个与所展示的不同则拒绝（`changed-during-confirmation`）；这种情况下不记录任何东西。
- 它会准确打印董事会在该检查点必须阅读的内容（`org/checkpoints.yaml`），董事会输入的可选备注成为记录的一部分。
- 席位的环境中从不包含 `SSH_AUTH_SOCK` 或 git 凭据助手（[10-providers.zh-CN.md](10-providers.zh-CN.md)）。这条规则关乎 git 传输凭据，仍然保留；它与批准无关。

### 批准与单写者

批准记录只有连同其 `approval.recorded` 账本事件才构成权威，而只有写出该记录的那个 `keel approve` 进程才会追加该事件。`keel approve` 获取账本写者锁，并像其他每个会改变状态的动词一样等待监督者锁，因此席位运行期间不会记录任何批准；摄入时的窗口检查只接受负责监督的进程自己的追加：在运行窗口期间出现的 `approval.recorded` 事件是外来的，会使该次运行被置为 `blocked(reserved_op)`（[04-trace-and-state.zh-CN.md](04-trace-and-state.zh-CN.md)）。

对席位而言，其后果是：它们产生的任何文件、投递、消息或账本行都无法成为批准：`.keel/approvals/` 下没有对应事件的文件会被忽略，并且也会使 `submit.frozen-paths` 失败；声称“已批准”的投递或最终消息只是数据；席位的完成声明由重新执行的证据来核对。`keel doctor --section approvals` 列出没有事件的记录、内容已变化的批准，以及即将过期的文档或策略。

## 暴露面画像与已知局限

暴露面画像说明：对于一个操作系统上、采用一种认证模式的一个运行时，席位进程能触及什么。`keel doctor --section exposure` 计算它，派发时将其冻结进运行记录，每份回执以及看板的运行时健康视图都会展示它。依据它采取行动的规则（拒绝在已暴露路由上运行代码执行类席位，且不提供董事会确认的放行路径）位于 [10-providers.zh-CN.md](10-providers.zh-CN.md)。

### 字段

| 字段 | 取值 | 含义 | 如何确定 |
| --- | --- | --- | --- |
| `tool_env_exposure` | `scrubbed`, `exposed`, `unknown` | 由席位的工具启动的进程是否继承模型提供方的环境变量取值 | 描述符中的环境清洗控制，按运行时版本经探测验证 |
| `tool_file_exposure` | `none`, `blocked`, `exposed`, `unknown` | 席位的工具能否读取仅含名称的模型提供方路径集 | `none`：集合中没有任何路径存在，只用 stat 测试，从不打开。`blocked`：禁止规则或独立的席位操作系统账户，经探测验证 |
| `control_plane_exposure` | `sandboxed`, `exposed` | 席位能否写入 `.git/keel` | 运行时的写边界。Codex 沙箱只限制写入；在所有操作系统上读取都不受限制 |
| 保留操作预防 | 按机制 | 哪些保留操作是被阻止的，而不只是被检测到 | 按运行时 shell 的权限规则、PreToolUse 守卫、席位 git 环境加固和 shim 覆盖范围 |

每条规则都把 `unknown` 当作 `exposed` 处理。

### 预防与检测

| 关注点 | 在以下情况下被阻止 | 始终由以下方式检测 | 未覆盖 |
| --- | --- | --- | --- |
| 席位进行批准，或批准被套用到已变化的内容上 | `keel approve` 在运行内拒绝执行；确认绑定所展示的内容 | 要求记录加账本事件；每道门禁处重新哈希；窗口检查 | 拥有用户权限、把记录、账本和锚点一起写入的进程（不在范围内） |
| 证据伪造 | `control_plane_exposure: sandboxed` | 落地重新执行 | 对落地决策而言无 |
| 账本编辑与伪造追加 | `control_plane_exposure: sandboxed` | 哈希链、对照锚点引用的尾部检查、摄入时的窗口检查、批准记录中的链头 | 比运行窗口活得更久的进程（局限 11）；把一切一致地改写的同一账户进程（不在范围内） |
| 引用移动与历史改写 | 梯级 A 和 B 上的权限规则和钩子 | 引用快照差异比对 | 无 |
| 推送 | 无效的按工作树 `pushurl`、重置的凭据助手 | 每次运行前后的 `git ls-remote` | 用席位自己的凭据推送到未配置的 URL |
| 读取模型提供方取值 | `scrubbed` 环境以及 `none`/`blocked` 文件 | 摄取时对工具事件的检查 | 由测试或声明的命令运行的代码 |
| 在 write_set 之外写入 | 运行时存在路径权限时 | 提交时的范围检查 | 对落地决策而言无 |

### 已知局限

1. 原生 Windows 对大多数智能体 CLI 没有操作系统级的写或读边界。除非使用可选的独立席位操作系统账户（M6，待探测验证），席位都以用户的文件权限运行。
2. Codex 沙箱只限制写入。在所有操作系统上读取都不受限制，因此它的 `sandboxed` 控制平面取值只涵盖写入。
3. 在原生 Windows 上，同一操作系统账户下由测试或声明的命令运行的代码无法被完全隔离。摄取检查只能看到工具事件，看不到测试进程做了什么。
4. 使用席位自行获得的凭据推送到一个未配置为远端的 URL，无法被 `git ls-remote` 检测到。服务端保护弥补了这一缺口。
5. 建议性 shim（sh、`.cmd`、`.ps1`）会被 Node 和 Rust 的进程启动以及 Git Bash 对裸名称的解析绕过。doctor 按运行时 shell 报告 shim 覆盖情况。
6. 钩子失败时放行（fail open），并且只在运行时信任该项目的地方加载。它们发出警告；由门禁做决定。
7. 模型家族独立性是董事会的声明，显示为"declared"（已声明），从不显示为"verified"（已验证）。在 P1 下 keel 无法检查端点或模型名；可选的相同/不同检查在内存中比较运行时报告的 id，不持久化任何东西。
8. keel 不控制席位进程的网络出口。
9. 批准记录证明的是 `keel approve` 记录了一次针对特定内容的确认，而不是谁确认了它、或它在真实时间中何时发生。批准人姓名是声明的，时间是本地时钟。
10. 克隆或归档把批准记录展示为过程历史。keel 不声称记录能在另一台机器上被验证为真实，只声称它可以被读取、其哈希可以被比对。
11. 账本事件由哈希链、锚点引用和摄入时的窗口检查保护，从不由签名保护。评审结论、ACK 和结果确实会决定落地，因此正是窗口检查让席位无法批准它自己的轮次。残余缺口是比运行窗口活得更久的进程：keel 在摄入之前会结束席位的整个进程树（`taskkill /T /F`），但逃出该进程树的进程（例如通过计划任务或服务启动的进程）可以在窗口验证之后追加事件并移动锚点，而之后的 Steward 进程无法把这些追加与它自己的追加区分开。可选的隔离席位操作系统账户（M6）可以为席位堵住这一缺口；它不覆盖、也无意覆盖以用户身份行事的同一账户进程（不在范围内）。
12. 批准记录中的链头是一致性检查。一个把记录、账本和锚点一起改写的进程不会给 `keel audit` 留下任何可察觉之处；那是与上面相同的、不在范围内的行为者。

## 哈希链与重新执行

由于在大多数原生 Windows 路由上席位都能写控制平面，keel 从不以"无法触及"作为论据。席位可能伪造的每条记录，要么被纳入哈希链并锚定在席位无法悄悄编辑的文件之外，要么由 Steward 在已验证的窗口内亲自捕获，要么在它能决定任何事之前被重新计算；唯一的残余途径是已知局限 11。本节论证的是一致性以及对席位活动的检测，而不是抵御拥有用户权限的同一账户进程（局限 12）。账本格式见 [04-trace-and-state.zh-CN.md](04-trace-and-state.zh-CN.md)；消费这些记录的门禁见 [11-verification.zh-CN.md](11-verification.zh-CN.md)。

```mermaid
flowchart LR
  e1["EVT n-2<br/>hash h1"] --> e2["EVT n-1<br/>prev h1, hash h2"] --> e3["EVT n<br/>prev h2, hash h3"]
  ap["批准记录 AP-...<br/>ledger_chain_head = h2"] -.->|"引用"| e2
  e3 --> tail["Steward 尾部检查：<br/>文件尾部等于锚点引用"]
  anchor["refs/keel/ledger/head<br/>（位于派生前的引用快照中）"] -.->|"每次追加后 CAS"| e3
```

| 席位可能伪造的记录 | 为何伪造决定不了任何事 | 在哪里检查 |
| --- | --- | --- |
| 一行账本 | 每个事件都携带前一个事件的哈希；每条批准记录引用链头；每个 Steward 进程在每次追加前对照锚点引用检查尾部；`keel audit` 报告 `chain-break` | [04](04-trace-and-state.zh-CN.md) |
| 追加的事件，例如 `verdict.recorded`、`ack.recorded`、`result.submitted` 或 `approval.recorded` | 摄入时的窗口检查只接受负责监督的进程自己的追加；为掩盖伪造追加而移动锚点的席位会造成一次引用变更，被派生前的引用快照捕获（`blocked(reserved_op)`） | [04](04-trace-and-state.zh-CN.md)、[05](05-vcs.zh-CN.md) |
| 认领状态 | 认领状态由账本事件推导；认领引用只是一个持有令牌的只可创建（create-only）CAS 锁 | [06](06-parallelism.zh-CN.md) |
| 一个 EV 文件 | EV 文件只是缓存。落地时在集成提交的全新分离检出上、在进程内重新运行完整的验收矩阵；落地前的复用要求源状态匹配字段完全相同 | [11](11-verification.zh-CN.md) |
| 一个 VD 文件 | 评审结论在摄取时从子进程的最终消息、MCP 提交或发件箱中捕获，并绑定提交与契约哈希；VD 文件只有配上来自已验证窗口的 `verdict.recorded` 事件才算数 | [11](11-verification.zh-CN.md) |
| 丢到 `.keel/approvals/` 下的一条批准记录 | 只有连同由运行窗口之外的 `keel approve` 进程写入的 `approval.recorded` 事件、匹配的主题以及当前内容哈希才算数；席位对 `.keel/**` 的写入也会使 `submit.frozen-paths` 失败 | [02](02-alignment.zh-CN.md)、[ADR-0005](adr/ADR-0005-explicit-confirmation-approvals.zh-CN.md) |
| 一个归档投影 | 投影是持久的历史，从不作为输入；批准从 `.keel/approvals/` 和账本重新核对，证据重新执行，从不从归档中读回 | [04](04-trace-and-state.zh-CN.md) |
| 带 keel 提交尾注的提交 | 只有 Steward 提交；席位产生的提交保存在 `refs/keel/snap/` 下，从不被信任 | [ADR-0004](adr/ADR-0004-steward-commits-and-submit-channels.zh-CN.md) |

以上每一项都有一个固定了失败原因的负对照，其中包括：链编辑会被检测到，运行期间追加的伪造 `verdict.recorded`（无论是否移动锚点）会在摄入时被发现，伪造的 EV 文件会被落地重新执行忽略，植入的推送会通过 `git ls-remote` 被检测到，植入的引用移动会被快照差异比对检测到。

## 不可信数据

模型、运行时或第三方产生的一切都是数据。权威只来自董事会由 `keel approve` 记录的显式确认，以及 Steward 代码（KP-04）。

| 来源 | 处理方式 |
| --- | --- |
| 席位投递：ACK（复述确认）、结果、评审结论、裁定、提问、分诊记录 | 摄取时进行 schema 校验；id 集合与简报（brief）做差异比对；从不执行；超出决策边界或落在停止类别上的裁定会被标记 |
| 声称已获批准、同意或已完成的席位文本；席位写到 `.keel/approvals/` 下的文件；行为者自称 `board` 的账本行 | 不作为权威，予以忽略。批准只以 `keel approve` 连同其账本事件一起写出的记录的形式存在；完成声明由重新执行的证据来核对，从不被当作董事会的决定 |
| 仓库内容、issue 文本、代码注释、测试输出、席位抓取的页面 | 可能携带提示注入。席位不能批准、落地、认领或移动引用；四种停止类别强制向董事会提问；范围检查、棘轮和无上下文的评审镜头限制了损害；董事会阅读回执 |
| 运行时记忆、会话历史、压缩摘要 | 不可信（这一思路取自 OpenHands）。压缩之后，简报摘要从 Steward 编译好的简报重新注入，而不是从记忆中 |
| 运行时的项目配置层和共享设置（`.codex/`、`.gemini/`、`.qwen/`、`.claude/settings.json`） | 从不读取、写入或依赖它们进行约束执行。keel 打印配置片段；信任绕过标志只在 `keel approve --rule override` 之后使用；从不生成 `--dangerously-bypass-hook-trust` |
| 钩子输出，包括压缩后的输出 | 仅作建议；连同分母记入日志 |
| 模型提供方的错误正文和运行时的自由文本错误 | 不持久化（类型化字段白名单）；原始流在内存中解析，从不写入磁盘 |
| 运行时报告的模型 id | 仅用于可选的内存内相同/不同检查 |
| 克隆上的归档投影和账本片段 | 仅用于展示和作为过程历史；批准对照记录和账本重新核对，而不是取自投影 |
| 在 keel 之外产生的人工提交 | 在通过 patch 轨道或已批准的 `--rule override` 采纳之前不被追溯 |
| 索引输出（codegraph、SCIP、启发式、LLM） | 每条边都带有来源；启发式和 LLM 边从不使门禁失败 |
| 看板 serve 请求 | 仅回环，检查 Host 和 Origin，只读 |
| MCP 工具调用 | `keel_submit` 只写入运行的发件箱；Steward 校验每一次投递 |
| 发往子进程的字符串 | argv 由描述符模板构建；从不使用 `shell:true`；长文本通过 stdin 或文件传递 |

## 服务端分支保护建议

keel 的保留操作检测是本地的。它无法阻止使用席位自行找到的凭据进行的推送，也不管辖其他机器推送的内容。服务端规则弥补这一缺口。keel 从不配置代码托管平台；以下是给董事会的建议，确切的设置名称因平台而异。

1. 保护主干：禁止强制推送和删除。
2. 只允许董事会身份向主干推送和合并。席位环境不携带任何代码托管平台凭据：keel 为席位重置 `credential.helper`，从不传递凭据助手，平台令牌也不应存放在席位会继承的变量中。
3. 优先采用仅快进或线性的主干。keel 使用 `merge --ff-only` 或 CAS `update-ref` 落地，因此主干上出现外来的合并提交，意味着有一个提交仍需采纳。
4. 在平台支持引用模式规则的情况下，拒绝推送 keel 的本地工作引用（`keel/*` 分支和 `refs/keel/*`）。它们是本地状态，而推送是保留操作。
5. 从 M1b 起，要求一个在主干顶端运行 `keel check --gate land --check approval --at <sha>` 的 CI 状态检查，使每个治理提交都携带一条哈希与已提交内容相符的批准记录。确切的 CI 调用方式在 M1b 发布时确定。
6. 将 `.keel/approvals/`、`.keel/charter.md` 和 `.keel/routing.yaml` 纳入平台的代码所有者评审。在多人共用一条主干的场合，把一次批准归属到某个人的，是平台的身份和评审规则；keel 的批准人字段只是一个声明的名字。
7. 保护发布标签。

推送到共享远端仍然是保留操作：董事会在 `keel land` 之后推送。多机协作是一项开放决策（[17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md)）；在它确定之前，其他机器只能看到已提交的批准记录和归档投影，且仅作为过程历史。
