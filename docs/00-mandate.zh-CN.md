# 所有者纲领：核心设计文档

> 英文原文（规范版本）：[00-mandate.md](00-mandate.md)。本文是其简体中文镜像，两者不一致时以英文版为准。

本文档是 keel 设计的根。它记录所有者对 keel 应当成为什么的声明，并把它重述为其他每份文档都由此派生的
约束性需求（R1 到 R5）、决策（D1 到 D7）和常设偏好（P1 到 P5）。它还负责刷新纪律（P4）：在每次重构评审时，
keel 的设计如何对照其参考项目重新审视；以及设计迭代纪律（P5）：在 keel 自身设计中发现的缺陷如何登记、走查、
决定和关闭。

优先顺序很简单。所有者声明高于本仓库中的其他一切。当另一份文档、一个 schema、一份模板或一个数据文件与它不一致
时，错的是那个文件，并予以纠正；只有当所有者更改声明时，本文档才会更改，而且它始终读起来就是当前的纲领：声明的历史就是本文件的 git
历史。[00-vision.zh-CN.md](00-vision.zh-CN.md)
展示设计如何满足每项需求，每个机制的归属见 [README.zh-CN.md](README.zh-CN.md) 中的单一归属表。

## 1. 所有者声明

1. 一个全新独立设计的工作流，借鉴现有工作流：OpenSpec、codegraph、edikt、keel（即无关的 dcsg/keel，致谢时记为
   keel-other）、oh-my-claudecode、oh-my-codex、old-coder、rtk、OpenHands、BMAD-METHOD、superpowers 以及其他设计
   得好的工作流，吸纳它们的设计优点。Kiro 不开源，所以只参考它的公开文件。keel 不是所有者此前工作流设计的
   后继者；那些设计的名称构成 D2 术语列表。
2. 架构可视化：融合 Sourcegraph、arch-viewer 这类做法。
3. 跨模型可用：Claude、Codex、Gemini、Qwen、Kimi、GLM、OpenCode 都能用。
4. 版本工具：git 为主，jj 只是可选增强，用于版本并行和追溯。
5. 设计文档：中英双语。
6. 人工审批：人类查看具体变更后批准。批准记录绑定明确的审批对象、产物哈希、批准人和批准时间。已批准对象的
   内容发生变化后，原批准失效，需要重新查看和批准。AI 席位的完成声明、评审结论和自行生成的批准文本，不能
   代替用户批准。不使用 SSH 签名，不引入密钥管理、签署者公钥名单、ssh-agent 枚举、硬件类型判断、逐次用户在场
   验证或独立身份认证系统。这里保护的是协作流程中的人工决策权和批准内容的一致性，不要求对同一操作系统账户
   下的恶意程序提供密码学防伪造保证。
7. 技术栈：TypeScript/Node CLI 加 Markdown；有前端展示时必须使用 TanStack。
8. keel 运营一家由担任各角色的 AI 员工组成的公司，其与工作目标的一致性靠机制保证，而不是靠说服。
9. M0 只交付一套设计文档和一个仓库骨架。
10. 许可证：MIT，“Copyright (c) 2026 Qither”。
11. 模型提供方的端点、密钥和模型名称属于用户；keel 从不读取任何模型提供方的值或凭据文件。
12. 借鉴思想，绝不借用依赖或文本。

常设指令：每次重构评审时，都要把上面提到的每个框架拉取最新版本到本地克隆，分析它们新增了什么，并当成初次的
全新设计一样，去检查和纠偏当前的工作流设计。每次重构时，还要到 GitHub 上查询是否有新的、设计优秀的工作流设计
可以融合进当前工作流；提示所有者把它们拉取到本地分析，并融合到当前工作流中。把以上内容转写为核心设计文档。

常设指令（设计迭代）：针对评审发现的这些设计问题，要设计核心的工作流设计迭代步骤，并追加到 00-mandate 文档中；
先不要着手解决问题，而是完善迭代步骤，后续依赖迭代步骤来解决这些设计问题。

## 3. 优先顺序与修订

优先顺序，从高到低：

1. 第 1 节中的所有者声明；其条款高于第 2 节中的重述，而第 2 节的表行是其他每个文件所依据的权威形式；
2. [00-vision.zh-CN.md](00-vision.zh-CN.md) 中的原则 KP-01 到 KP-16；
3. 每个机制的归属文档（[README.zh-CN.md](README.zh-CN.md) 中的单一归属表）；
4. keel 自身的 ADR；按建议采纳的决策可以通过改写其 ADR 撤销；
5. schema、数据表、模板、示例和纯类型代码，它们实现上述文档。

高层级胜出，低层级被纠正。变更规则：

- 只有所有者能修订声明：在与维护者的对话中、在 issue 中，或在所有者本人提交的 commit 中。声明就地改写，
  使本文档始终读起来就是当前的纲领；什么改了、何时改的，只以本文件的 git 历史为准。
- 一次修订与它影响的每个文件落在同一个 commit 中：第 2 节的表、[00-vision.zh-CN.md](00-vision.zh-CN.md) 中的需求
  映射、各归属文档、记录该决策的 ADR、[17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md) 和
  [16-sources-credits.zh-CN.md](16-sources-credits.zh-CN.md)。任何文档都不保留变更日志、“由……修订而来”的说明
  或自身被取代的旧版本；`git log` 和 `git diff` 就是记录。该 commit 中 `npm run check` 必须通过。
- 当某条款有歧义时，优先采用能让其他每条条款都成立的解读，并通过 [17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md)
  把问题交给所有者，而不是悄悄自行解决。当下游文档无论怎样解读都无法让某条款成立时，这是一个类别为
  `mandate-conflict` 的设计问题，由第 5 节登记并交给所有者。


## 4. 刷新纪律（P4）

所有者的常设指令，以流程的形式写出。其目的是让 keel 在参考项目演进时持续借鉴其精华，并且每次都重新评判设计，
而不是为其辩护。

### 4.1 何时运行刷新评审

- 在从 M1a 到 M8 每个里程碑的退出评审时（[15-roadmap.zh-CN.md](15-roadmap.zh-CN.md) 把它列入退出条件）。
- 每当所有者要求对 keel 做设计评审或重构时。
- 在采纳一个新的参考项目之前。
- 普通变更（一次 schema 修正、一次翻译、一个探测结果）不运行；它们引用最近一次评审。

### 4.2 参考项目登记表

`docs/reference-projects.yaml` 是规范的登记表，由 `schemas/reference-registry.schema.json` 校验。每个参考项目
一条记录：上游、许可证与许可证类别、是否由所有者点名、其本地克隆相对于本仓库的位置，以及评审历史（日期、HEAD、
非上游默认分支时的分支、版本、范围、结果）。它还保存搜寻记录：常设的 GitHub 查询、最近一次运行，以及每个候选
项目及其状态。
[16-sources-credits.zh-CN.md](16-sources-credits.zh-CN.md) 中的构件映射说明 keel 借鉴了什么；登记表说明审视了
什么、何时审视。本地克隆放在 keel 检出目录旁边；keel 从不提交它们，`scripts/validate.mjs` 也从不打开它们。

### 4.3 流程

1. **拉取。** 对登记表中每个有本地克隆的条目，抓取并快进该条目记录的分支（未记录时为上游默认分支），记录新的
   HEAD、日期和版本。克隆缺失，或其许可证文件发生变化的，在读取其他任何内容之前先行报告。由所有者点名、有上游
   但没有本地克隆的条目（arch-viewer、Sourcegraph），在下一次评审的第 5 步向所有者提出拉取请求；克隆后读取其
   许可证文件并记录 `licence_class`。对以 npm 包形式使用的参考项目（TanStack，以及随它一起评审的 React），
   记录最新发布版本和 `package-lock.json` 中锁定的版本，阅读两者之间的变更日志，并把主版本号的变动当作第 3 步
   的一个设计元素；第一次这样的评审在 M5 退出时进行，版本取自 lockfile，`head: null`。每个这样的包在首次加入
   `package.json` 时即读取其许可证文件并记录 `licence_class`，早于第一次评审，因此不会出现某个包已被打包进
   产物、而第 4.5 节的护栏仍把它归为未核实的情况。
2. **比对。** 阅读自上次评审的 HEAD 以来的变化：发布说明、变更的文档、新的命令、schema、钩子和工作流。每个新
   的设计元素用一行记下，并附指向克隆内的位置。
3. **重新推导。** 把 keel 当作初次设计。对每条原则 KP-01 到 KP-16 以及
   [16-sources-credits.zh-CN.md](16-sources-credits.zh-CN.md) 中的每一构件行，追问新的证据是证实它、细化它还是
   与它相矛盾。矛盾即意味着纠正：修改归属文档，并在某项已记录的决策翻转时附上取代它的 ADR。绝不绕着它打补丁。
   keel 自身文档内部的矛盾（而不是 keel 与参考项目之间的矛盾）作为设计问题登记到第 5 节，并通过该流程纠正。
4. **搜寻。** 使用登记表中的常设查询，在 GitHub 上搜索自上次评审以来发布或有实质变化的工作流和智能体编排设计。
   候选项目须满足：开源或有公开文档、许可证允许 keel 从中学习、有真实使用的证据，并提供 keel 缺少或做得更差的
   机制。记录每个候选项目的上游、许可证、keel 可能借鉴什么以及原因。
5. **提示所有者。** 按第 4.4 节的形式呈现候选项目，然后停下。由所有者把候选项目拉取到本地克隆，或批准拉取。在
   此之前，不从候选项目中采纳任何东西。
6. **融合。** 对每个采纳的思想：在 [16-sources-credits.zh-CN.md](16-sources-credits.zh-CN.md) 中添加一行构件
   及其被允许的来源、修改受影响的归属文档、添加登记表条目，并在某项已记录的决策变更时附上取代它的 ADR。P3 和
   D2 全程适用：只借思想，绝不借文本或代码；不用禁用术语；ELv2 和非开源来源只贡献思想。
7. **记录。** 把本次评审追加到每个条目的历史和搜寻记录中，然后运行 `npm run check`。

### 4.4 向所有者提出什么

一条消息，一张表：候选项目、上游、许可证、它做什么（一行）、keel 可能借鉴什么，以及是否把它拉取到 keel 检出
目录旁的克隆中以供分析的问题。同一条消息还为现有参考项目列出每次 HEAD 移动及其中发现的设计元素。所有者对每个
候选项目作答：拉取、拒绝（连同原因记入登记表）或推迟。

### 4.5 护栏

- 许可证类别决定用法：开源贡献由 keel 重新实现的思想；ELv2 之类的源码可得（source-available）许可证只贡献思想，
  并接受形态审计；专有产品只通过公开文档贡献；未核实（unverified）的许可证按专有对待，直到其许可证文件被读取
  并记录类别，时机是某次刷新评审，或对 npm 包而言是它首次加入 `package.json` 之时（第 4.3 节第 1 步）。
- 刷新评审从不自行扩展 D2 术语列表；新的禁用名称来自所有者。
- 评审期间 P1 仍然有效：审视参考项目从不涉及读取所有者的模型提供方或凭据文件，即使该参考项目把它们放在众所周知
  的位置。
- 刷新评审从不更改第 1 节中的声明。


## 5. 设计迭代纪律（P5）

所有者的第二条常设指令，以流程的形式写出。第 4 节向外看，把 keel 对照参考项目重新推导；本节向内看。它把在
keel 自身的文档、schema、模板和表中发现的每一个缺陷推进到一个决定和一次关闭它的 commit，并阻止同一形态的
缺陷再次被写出来。它针对的形态有四种：规则变更后其消费方没有被重新走查；一个术语承载两个含义；一条步骤链
无法走完或一个等待无法被释放，而这类问题只靠散文永远显示不出来；第 1 节的某条款被下游文档的改写悄悄调和，
而不是交给所有者。

### 5.1 何时运行设计迭代

- 任何人（所有者、维护者、参与开发 keel 的代理、外部评审）发现两句陈述不能同时成立、某一步需要只有后一步
  才产出的产物、某个等待只能由被等待的那一步结束、一个术语有两个含义、一个字段没有任何读者，或者某条路径向
  董事会索取的确认多于纲领所需。发现即登记（第 5.3 节第 1 步），然后才修正任何东西。
- 在某个 commit 于归属文档、schema、模板或 `org/` 表中引入、收紧或放松一条规则之前。规则指：前置条件
  （"only when"、"requires"、"needs"），等待、锁或拒绝（"waits for"、"until"、"no exception"、"refuses"），
  存放位置（"is written"、"committed"、"projected"、"checked" 于某处或自某处），基数（"exactly one"、
  "at most"、"every"、"never"），由公式定义的度量，以及 schema 的 required 字段或枚举值。该 commit 必须携带
  第 3 步对该规则的走查。这是轻量模式：流程中唯一允许规则变更单独运行的部分，而且它从不跳过走查。
- 当刷新评审的第 3 步（第 4.3 节，重新推导）发现 keel 文档内部的矛盾时：在这里登记，而不是在那里打补丁。
- 在从 M0 起每个里程碑的退出评审时，先于刷新评审：登记表中的 `exit_review` 被设为该里程碑，`issues`
  检查随之成为退出门禁（第 5.2 节）。
- 当 `scripts/validate.mjs` 的 `issues` 检查因设计原因而非错字失败时。
- 每当所有者要求设计评审或重构，或报告一个缺陷时。
- 翻译、错字、示例数据或探测结果不触发；它们不改变任何规则，也不引用任何问题。

### 5.2 设计问题登记表

`docs/design-issues.yaml` 是规范的登记表，由 `schemas/design-issues.schema.json` 通过 `examples` 检查校验，
并由 `scripts/validate.mjs` 的 `issues` 检查交叉核对。它保存四样东西，全部只是当前状态，从不是叙事：

- `issues[]`：每个发现一条记录，`DI-nn`，包含标题、一段用 keel 自身术语写成的陈述、冲突文字所在的锚点
  （一个文件加一个标题，或一个文件加一个 JSON 指针；绝不是行号）、发现者、类别、状态、根因、第 3 步的走查、
  第 4 步的术语、选项与建议、决定、它阻塞的里程碑，以及关闭证据。类别按优先序为：`mandate-conflict`
  （第 1 节的条款、第 2 节的行或某条 KP 与更低层级相冲突）、`cycle`（某一步需要后一步才产出的产物、某个等待
  只能由被等待的那一步结束，或者消费方所在机器无法到达的存放位置）、`term-collision`（一个术语两个含义，或
  两个术语一个东西）、`gap`（设计未定义的状态、没有读者的字段，或者过弱而撑不起所倚赖之声称的生产方）和
  `cost`（索取多于纲领所需的仪式）。状态：`open`、`analysed`、`proposed`、`decided`、`closed`；`deferred`
  只能由所有者决定并指向一个具名里程碑；`dismissed` 须附理由。已关闭的记录永不删除。
- `order`：设计的常设顺序图，而不是逐问题的备注。`steps[]` 是动词、门禁和阶段步骤，带有 `after` 边和它们
  运行所在的机器（`runs_in`：local、supervisor、seat 或 clone）；`artifacts[]` 指明产出每个产物的步骤、
  需要它的步骤以及它的存放位置（`where`：工作树、git common dir、`refs/keel`、提案分支、主干提交或归档
  提交）；`locks[]` 指明每把锁由谁持有、谁在等待、哪一步释放。每个条目都锚定到陈述它的标题。`issues` 检查
  遍历该图：一个环，或者某个产物被一个其所在机器无法到达其存放位置的步骤所需要（克隆只能到达主干提交和
  归档提交；席位只能到达它的工作树和提案分支），都是错误，除非该条目被标记了一个开放的问题；标记指向已关闭
  或已驳回的问题也是错误，因此已关闭的问题不能继续容忍它的边。
- `matrix`：走查矩阵，轨道 × 行动者 × 序列。行动者是常设的：终端前的董事会、波次进行中的董事会、负责监督
  的 Steward、监督者锁被持有期间的第二个 Steward 进程、席位、运行时钩子、全新的 CI 克隆、崩溃的监督者、
  第二台机器和看板。序列是每个轨道的正常链以及各种中断：hold、abandon、override、修订案、崩溃与恢复、第二次
  land、主干顶端的 CI 检查。
- `walkthroughs[]`：只追加的走查历史，最早的在前，每条记录其触发条件、走过的格以及它登记或重走的问题。

填满顺序图并把矩阵的每个格走过一遍，是本流程的第一次运行，即基线走查；[15-roadmap.zh-CN.md](15-roadmap.zh-CN.md)
中 M0 的退出条件要求它。当 `exit_review` 被设置时，`issues` 检查对每个阻塞该里程碑或更早里程碑、且未关闭、
未推迟、未驳回的问题报错，也对每个尚无类别的开放问题报错。

### 5.3 流程

1. **登记。** 每个发现一条登记表记录，状态 `open`：标题、陈述、锚点、发现者和对根因的猜测。复合的发现要拆开，
   所以一个环和一个不可到达的位置是两条记录。第 3 节排在较低层级的文字原样保留：不改写任何文字来让一个
   发现消失，任何文档也不因此增加备注。
2. **归类。** 按第 5.2 节的优先序取恰好一个类别。锚点落在本文档第 1 节或第 2 节、或某条 KP 上的记录，
   由构造即为 `mandate-conflict`，绝不由判断决定。`blocks` 是最早的那个其范围会建造该规则的生产方或消费方的
   里程碑，或者所有者确认某个会被修正改动的按建议采纳行的那个里程碑；绝不只是首次运行到该规则的里程碑。
3. **走查。** 对记录点名的每条规则，以及轻量模式下 commit 改动的每条规则，把四项事实写入登记表，绝不只写在
   commit 信息里：
   - 生产方：对规则陈述的每个前置条件，写下产出它的步骤、该步骤在序列中位于消费方之前还是之后，以及它的
     产出是否足以支撑规则所倚赖的性质（完整对深度受限、已证明对启发式或仅建议、新鲜对缓存）；靠后或不足的
     生产方是 `cycle` 或 `gap`；
   - 消费方：从规范表推导（[12-cli-api-mcp.zh-CN.md](12-cli-api-mcp.zh-CN.md) 的动词与模式表、
     [11-verification.zh-CN.md](11-verification.zh-CN.md) 的门禁目录、链接到该规则归属文档的那些文档），
     绝不只靠文本搜索；对关于锁、等待或拒绝的规则，每个动词模式一行，写明它等待什么、由什么释放，再加上固定
     的一行“持有者崩溃或永不释放”；某一行的释放条件正是该模式存在的目的所要造成的结果，即为死锁；
   - 位置与行动者：每个产物存放在哪里，每个消费方由哪台机器上的哪个行动者运行；“after X, Y”、“X is
     committed in Y”和“X is checked from Y”与“before”和“requires”一样都是顺序边；行动者到不了的位置是
     `cycle`；
   - 读者与计数：每个 required 字段、枚举值和公式定义的度量都至少列出一个读者（动词、门禁、记录、视图或
     度量）；一个也没有是 `gap`；一个公式两个名字，或名字的声称超过其公式，是 `term-collision`；对关于董事会
     检查点或工单的规则，按轨道、路线（逐次契约或策略路径）和拓扑（共享主干或单人）计算确认次数和工单数，
     并与每句基数陈述以及 [15-roadmap.zh-CN.md](15-roadmap.zh-CN.md) 的确认次数度量比对。
   走查点名的步骤、产物和锁进入顺序图，然后运行 `issues` 检查。走查让某条边变红的 commit 不得落地，除非
   同一 commit 登记了该问题。
4. **审计术语。** 对规则所倚赖的每个名词（“proves”、“guarantees”或“ensures”的主语；“only when”或“once”
   之后的条件），把归属定义引到声称旁边，写明声称要求什么、定义提供什么。有界定义撑无界声称是
   `term-collision` 或 `gap`。一个术语、一个含义、一行术语表、一个归属：第二个含义得到自己的英文标识符和
   [00-vision.zh-CN.md](00-vision.zh-CN.md) 术语表中自己的一行，而且只要任何保留用法的要求仍超过定义所
   提供的，问题就绝不通过改名关闭。
5. **分流。** 以下情形由所有者决定：类别为 `mandate-conflict`；修正会翻转
   [17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md)“由所有者解决”表中的决定；修正会改变董事会批准产物
   （章程、目标或路由）某个字段的含义；修正会改动按建议采纳的行。其余由维护者采纳登记的建议来决定，已记录
   的决策翻转时附上取代它的 ADR。当被改动规则的某个消费方是第 1 节的条款或第 2 节的行时，轻量模式不可用：
   该改动不落地，先登记并分流该问题，而下游句子给条款添加条款本身没有的限定词（"only"、"in memory"、
   "never persists"）是冲突的证据，绝不是条款成立的判定。
6. **提示所有者。** 按第 5.4 节的形式发一条消息，然后对每个交给所有者的问题停下。存在纲领冲突时，把它们单独
   列在最前面，在得到答复之前不编辑其下游的任何内容。
7. **修正。** 按顺序：先按类别，再按最早的 `blocks`；同一机制上仍有更高类别问题开放时，较低类别的问题等待。
   每个问题一个 commit，或共享同一规则的一组问题一个 commit：归属文档及其镜像、走查表上每个消费方标为
   changed 或 unchanged 并附理由、术语表行、实现它的 schema、模板、示例和纯类型代码、ADR、
   [17-open-decisions.zh-CN.md](17-open-decisions.zh-CN.md) 中的条目，以及当范围或退出条件变化时的
   [15-roadmap.zh-CN.md](15-roadmap.zh-CN.md)；第 1 节和第 2 节只来自所有者本人的话。环要先红后绿：先在
   顺序图中重现并标记其问题，然后才消除。每个引入等待的句子都要点名释放它的是什么；每个引入前置条件的句子
   都要点名产出它的是什么以及它存放在哪里。
8. **关闭。** 状态 `closed` 并附证据：M0 中证明关闭的 validate 检查，自 M1a 起 `test/` 中在缺陷回归时会
   失败的负对照（`cycle` 类必须有）；走过的格成为该记录的回归格。问题只在改动了走查表上每个消费方的那个
   commit 中关闭。
9. **记录。** 把走查追加到 `walkthroughs[]`，运行 `npm run check`。之后每次迭代和每次里程碑退出都先走回归格；
   回归重开原问题，而不是登记新问题。

问题按类别顺序处理：先 `mandate-conflict`，因为答案可能改变每个更低的修正；再 `cycle`，因为设计照现状无法
运行；再 `term-collision`，因为一个碰撞会藏住其他缺陷；再 `gap`；最后 `cost`。`cycle` 绝不由维护者推迟，
`mandate-conflict` 绝不由维护者修正。

### 5.4 向所有者提出什么

每次迭代一条消息，一张表：问题编号与类别、不能同时成立的那些陈述（各自引用其归属文档与标题）、选项、建议，
以及该问题阻塞什么。所有者逐条作答：选一个选项、推迟到某个具名里程碑、用自己的话重述条款（随后依第 3 节
用这些话就地改写第 1 节），或附理由驳回。存在纲领冲突时，它单独列在最前面。

### 5.5 护栏

- 迭代从不自行更改第 1 节中的声明。与声明的冲突只由所有者回答，下游文档从不为了让冲突消失而被改写，纲领的
  消费方从不由改动者本人判定。
- 文档只陈述当前设计：任何归属文档都不点名某个问题、某次修正或它取代了什么。登记表保存状态，git 保存差异。
- 一个术语、一个含义、一行术语表、一个归属；蓝图的固定词汇从不悄悄改名。
- 锚点是标题和指针，绝不是行号；失效的锚点使检查失败，并被修复而不是删除。
- `scripts/validate.mjs` 仍是唯一的工具例外且不含产品逻辑：`issues` 检查证明存在性、单一归属、无环和可达性，
  从不证明行为；行为自 M1a 起由负对照证明。
- 迭代不是刷新评审：它不拉取任何参考项目，也不采纳任何思想。当某个缺陷表明某个参考项目做得更好时，把候选
  项目记入第 4 节的搜寻记录。
- P1 和 D2 始终有效：不为重现问题而读取任何模型提供方的值，也不扩展 D2 术语列表。
- 轻量模式从不跳过走查，而且走查是登记表条目，绝不是 commit 信息里的备注。
